# Game Market — тестовое задание

FastAPI + PostgreSQL реализация витрины цифровых товаров. Главная цель — не допустить двойной выдачи кода при дублях, гонках и сбоях.

## Запуск

```bash
docker compose up --build
```

Откройте http://localhost:8000. API-документация доступна на http://localhost:8000/docs.

Остановить: `docker compose down`. Сбросить именно тестовую БД: `docker compose down -v`.

## Что реализовано

- витрина: шапка, карусель, каталог, сервисы, переключатель валют и карточки;
- live-витрина через Server-Sent Events: цена и остаток меняются во всех открытых вкладках без перезагрузки;
- резервирование конкретного ключа при переходе к оплате с видимым трёхминутным таймером; после таймаута ключ автоматически возвращается в наличие;
- создание заказа, эмуляция оплаты, durable webhook inbox и страница статуса;
- транзакционная выдача: `SELECT ... FOR UPDATE`, уникальные `event_id`, `request_id` и `order_id` в выдаче;
- два идемпотентных поставщика-заглушки: ручные режимы, настраиваемые вероятности ошибок/таймаутов и задержка ответа;
- админ-экран невосстановленных заказов, пополнение ключей и безопасный retry;
- промокоды с атомарным лимитом использований.

## Проверка гонок

В отдельном терминале после запуска приложения:

```bash
python3 tests/race_test.py
python3 tests/promo_race_test.py
python3 tests/recovery_test.py
python3 tests/stage2_race_test.py
```

Скрипт создаёт один заказ, одновременно отправляет 50 разных событий `paid`, затем проверяет, что у заказа один факт выдачи и один ключ. Повтор с тем же `event_id` также не меняет результат.

`promo_race_test.py` одновременно применяет `LIMIT3` к 20 заказам и проверяет, что промокод никогда не использован больше трёх раз. `recovery_test.py` имитирует сбой поставщиков и параллельно повторяет выдачу одного восстановимого заказа с тем же зарезервированным ключом. Для полностью чистого прогона бонусных тестов используйте `docker compose down -v` перед запуском.

`stage2_race_test.py` оставляет в пуле ровно один ключ и одновременно запускает два checkout-запроса. Успешен ровно один: второй получает `409` с понятным сообщением о распродаже. На `/admin` можно изменить цену или добавить ключи — открытые витрины обновятся автоматически. Поиск работает по мере ввода, а поисковая строка и фильтр сохраняются в URL.

## Почему выдача однократная

1. Вебхук сохраняется в `payment_events` с уникальным `event_id` до обработки. Неизвестный заказ остаётся в inbox и будет применён после его создания.
2. Переход к выдаче берёт строку заказа через `FOR UPDATE`; финальный заказ повторно не выдаётся.
3. Каждая поставка имеет стабильный `request_id`. Таблица поставщика хранит результат этого id, поэтому после таймаута повтор возвращает тот же код.
4. `deliveries.order_id` уникален, а ключ меняет состояние внутри одной транзакции PostgreSQL. Повторные воркеры не смогут записать второй факт выдачи.
